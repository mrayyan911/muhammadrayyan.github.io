## Technical findings

### T1. Sitemap dates predate significant content changes

Impact: low. Priority: P3, quick win.

Evidence: `sitemap.xml:5`, `:9`, `:13`, and `:17` all state `2026-09-24`. Commit `9478ad6`, dated 2026-09-28, changes homepage and arcade page copy. The live sitemap still uses the earlier dates.

Fix: update the affected entries to the actual significant-content modification date, 2026-09-28 for these edits. Maintain dates when meaningful content changes occur, or omit optional lastmod fields if accurate maintenance is impractical. Do not refresh them on every deployment. Google uses lastmod when it is consistently accurate. [Google sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).

### T2. Real-user performance remains unverified

Impact: unknown. Priority: P2, measurement task.

Evidence: a DevTools homepage reload at 390 by 844, DPR 3, unthrottled CPU and network, reported LCP 183 ms and CLS 0.00. This was a repeat visit with cache/service-worker effects, not a cold mobile benchmark. The tool reported no page-level CrUX data. No representative interaction session was recorded, so INP was not assessed. Arcade performance was not profiled.

Fix: establish cold-load mobile measurements and assess game interactions on representative devices. Use Search Console or available CrUX data for field assessment. Good field thresholds are LCP at most 2.5 seconds, INP at most 200 ms, and CLS at most 0.1, assessed at the 75th percentile. [Web Vitals guidance](https://web.dev/articles/vitals).

All four pages request a shared Google Fonts stylesheet containing four font families. It is a possible cold-load optimization target, not a proven bottleneck. Measure before reducing font usage or changing loading behavior. The unused 1.62 MB original portrait on disk is not evidence of homepage transfer bloat; the HTML requests resized WebP images.

Evidence: the titles at `arcade/index.html:7`, `arcade/cube/index.html:7`, and `arcade/chess/index.html:7` identify the collection or game, but omit the browser-play intent and distinguishing 3D/bot functionality.

Retain the clear existing homepage title. Its H1 identifies the person, while adjacent text identifies his role and location; there is no need to force every target phrase into the H1. Title and description character counts are editorial checks, not fixed Google eligibility rules. [Google title guidance](https://developers.google.com/search/docs/appearance/title-link).

## Content and authority findings

### C1. Project expertise has no dedicated search landing pages

Impact: potentially high for non-branded employer/client discovery. Priority: P2, strategic opportunity.

Evidence: `index.html:176` onwards presents JournalPost, Usage Pill, and Imagenix on one homepage. Project links lead to the live product or GitHub. The complete four-page inventory has no individual case-study URLs. Usage Pill and Imagenix already include useful server-delivered details, even though their disclosure panels start closed.

Fix: build one detailed case study first, based on the strongest evidence and desired work. Explain the problem, personal contribution, architectural decisions, constraints, and verified outcomes. Include relevant screenshots and links to source or the live product. Link the case study from its homepage project card, add a self-canonical, and include it in the sitemap. Do not invent metrics or create several near-identical technology/location pages.

Candidate topics, pending demand validation: a publishing platform built with Next.js and Payload CMS; a Claude Code/Codex usage-monitoring desktop app; or an image-dataset annotation pipeline. These are grounded in existing work, not researched keyword-volume recommendations.

### C2. Game pages provide little explanatory context beyond controls

Impact: medium if game-search acquisition becomes a goal. Priority: P4, optional under the confirmed employer/client goal.

Evidence: the rendered chess introduction is "You against the bot." The cube introduction is "Scramble it, then bring every face back to one color." Control descriptions exist in HTML disclosures, but broader orientation is brief.

Fix: add concise, useful instructions below the game: how to start, touch/mouse controls, difficulty or timer behavior, and verified save/resume behavior. Keep play immediately accessible. The functional game itself provides value; short text alone does not establish a thin-content penalty. No arbitrary word count or FAQ schema is warranted.

### Existing credibility and unverified authority

The homepage identifies the developer, location, experience, education, projects, contact address, resume, GitHub, and LinkedIn. These are useful credibility signals. Rendered ProfilePage/Person markup exists and references that identity. Presence and valid JSON parsing do not establish rich-result eligibility. Use the Rich Results Test for Google's validation. [Google ProfilePage guidance](https://developers.google.com/search/docs/appearance/structured-data/profile-page).

No backlink inventory or Search Console link report was available. Domain authority, link quality, ranking losses, and organic traffic cannot be assessed from outbound profile links. Keep professional profile website links consistent with the canonical domain and earn references through useful published work.
